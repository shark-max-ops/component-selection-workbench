# A3 第一步：版本化人工审核

本轮只实现实施计划中的 A3.1。人工对照 PDF 确认供电参数，宿主保存版本化审核记录并调用原供电规则，旧运行和旧判定保留。尚未实现 A3.2 的 LangGraph interrupt/resume，也未实现 A3.3 的工具超时、重试、取消及失败恢复。

## 操作

在 backend 启动 `uv run python -m scripts.run_terminal`。打开一个最新运行已 passed 的任务：

```text
/tasks
/open task-实际ID
/status
/evidence
/review review-001 | 0 | 审核人姓名 | approve | 已对照 PDF 核对推荐供电范围、单位及适用条件
/report
/reviews
```

`/status` 给出当前参数和 `review_revision`，首次审核版本为 0。请先对照证据定位的 PDF 页面，审核命令代表操作者确认已核对，程序不能替代人工阅读。审核人只是本地声明，没有身份认证；普通聊天不能提交审核。

3.3 V 在推荐范围内时，批准可使供电结果从 unknown 变成 satisfied；6 V 批准后仍为 not_satisfied。批准的是参数证据，不是强制批准器件。用新的请求 ID 和当前版本撤回：

```text
/review review-002 | 1 | 审核人姓名 | reject | 撤回确认，等待重新核对
```

撤回后结果为 unknown。审核不调用模型、不新建模型 run。可继续发送普通消息查看模型解释，程序报告必须与最新审核后的规则结果一致。其他 ADC 条件仍未核验。当前只确认或撤回原参数，不支持修改数值、条件或需求。

## 实现与保存边界

- `app/services/task_service.py` 的 `review_supply()` 校验请求字段、当前版本、绑定 PDF 哈希、参数与提取原文一致性，并要求最新运行已通过验收及检查点没有待执行分支。审核使用原 `check_supply_voltage()`，不改变规则。
- `app/services/reviews.py` 在每任务 `reviews.sqlite` 中保存审核人、时间、说明、决定、原/新业务快照及新报告；版本号主键和请求 ID 唯一约束保护有效记录。事实和规则结果的原语义 ID 保留，历史身份由 task_id、审核 revision 和运行 run_id 区分。
- 相同请求 ID、相同内容重放返回原版；同 ID 内容不同或非当前版本的新请求会拒绝。跨进程重放已验证。重放旧请求返回它自己的历史版本，当前结果以 `/status` 为准。
- `BEGIN IMMEDIATE` 锁覆盖服务的整次模型执行或审核；同任务第二个写操作立即失败，不排队和自动重试。不同任务使用不同数据库。进程结束会释放 SQLite 锁，但不意味着未完成模型节点可恢复。外部直接修改文件不受此服务锁约束。
- `get_task_status()` 只读返回最新已提交审核；审核库是审核后的业务结果来源。下一次续聊由宿主把最新快照通过 `Overwrite` 注入图输入，同时同步 `/inputs/review.json` 和 `/outputs/report.json`。普通业务工具仍使用原来的冲突检查 reducer；模型不能提交 Overwrite 或修改宿主审核库。
- 原 `task.json`、`/inputs/task.json` 和历史 run 不覆盖，创建时审核声明继续作为历史快照。每次 run 的 manifest 记录本次使用的审核版本。

审核库提交与 LangGraph 检查点之间没有跨库事务。审核提交后、续聊前，原检查点可能仍保存旧结果；查询统一读最新审核，下次续聊同步。不承诺图状态与审核库原子更新，不提供任意节点恢复、崩溃重放或工具恰好执行一次保证。失败/运行中的最新 run 会阻止新的审核；相同已提交审核请求的幂等读取仍可返回历史记录。

## 验证

使用合成文档和固定模型响应，实际运行图、工具、SQLite 与程序规则。覆盖批准/撤回、范围内外电压、历史保留、审核后续聊、跨进程请求重放、旧版本与冲突请求拒绝、输入校验、任务锁/隔离、失败后审核拒绝、只读查询和终端分发。

本轮未调用真实模型，也未替用户批准真实 PDF。离线跨进程请求重放不是“等待审核节点跨进程 resume”，后者留待 A3.2。

最终验证：Ruff 通过；全量离线测试 **62 passed in 44.92s**，包含新进程审核请求重放；`git diff --check` 无空白错误。测试耗时不作为性能指标。
