# A3 完整验收：人工审核、等待与有边界的故障处理

## 用容易理解的话说

工作台先按 PDF 提取 ADS1115 的推荐供电范围，规则计算“满足、不满足或待确认”。人工审核负责确认提取的参数和条件是否与原文一致。你可以让任务停下来等审核或澄清，退出后再打开原任务继续。供电证据提取如果临时卡住或出错，程序会在限定次数内重试；运行失败时，只有检查点已完成、没有待执行节点，才允许再恢复一次。每次运行和审核都有独立记录，旧结果不会被覆盖。

## 用实际任务查看和审核

在项目的 `backend` 目录执行：

```powershell
uv run python -m scripts.run_terminal
```

终端输入：

```text
/tasks
/open task-f65a204f0317416a9dee6033fc0fee9f
/status
/evidence
/report
/reviews
```

如果该任务未被你继续修改，`/status` 预计显示**等待人工输入**、需求 **3.3 V**、推荐范围 **2～5.5 V**、人工审核 **版本 1**、供电判定**满足**，并给出中断 ID 和恢复命令。`/evidence` 显示型号 ADS1115、手册 SBAS444E、PDF 第 4 页、5.3 节和原文；你应打开任务绑定的 PDF 对照型号、数值、单位和条件。`/report` 的程序结论是“满足”，并提醒其他需求仍未核验。`/reviews` 逐版显示审核人、决定、前后判定与说明。若当前任务状态已变化，以实际 `/status` 为准。

这个任务已经停在审核等待点。先退出再启动，确认等待没有丢失：

```text
/status
/exit
```

`/status` 仍显示 **等待人工输入**和一条完整 `/resume ...` 命令。退出不会丢失等待事项。重新启动终端、打开同一任务并再次查看状态。对照 PDF 后，使用当前版本提交新审核。以下版本号 `1` 仅是上述任务目前已知的示例：

```text
/open task-f65a204f0317416a9dee6033fc0fee9f
/status
/review a3-check-001 | 1 | 你的姓名 | approve | 已核对第4页推荐供电范围和适用条件
/status
```

预计审核版本变成 **2**，程序供电结论仍为**满足**，任务仍显示**等待人工输入**。复制 `/status` 给出的实际恢复命令，把其中的审核请求 ID 换成 `a3-check-001`：

```text
/resume 实际中断ID | a3-check-001
/report
/reviews
```

恢复后执行状态预计为**已完成**；`/report` 保留程序判定，`/reviews` 新增一条版本 2 记录。普通聊天消息、错误或其他任务的中断 ID 都不能代替 `/resume`。恢复步骤会调用模型，模型解释的用词可能变化；请以程序报告为准。若任务当前版本已不是 1，请用 `/status` 的版本号和新的请求 ID，别照抄旧版本。想再次体验“新建等待”，在已完成状态输入 `/wait-review`；`/status` 又会显示一个新的中断 ID。已有等待时不可重复输入 `/wait-review`。

## 可控故障验收，不影响真实任务

从 `backend` 目录用 uv 跑离线测试。每次创建新临时目录，避免碰已有运行资料：

```powershell
$testTemp = Join-Path (Resolve-Path ../runtime) ("tests-a3-" + [guid]::NewGuid().ToString("N"))
uv --cache-dir ../runtime/uv-cache run --offline --no-sync python -B -m pytest tests/test_bounded_extract.py tests/test_task_service.py::test_failed_supply_tool_recovers_once tests/test_task_service.py::test_cancel_request_is_persistent_and_idempotent tests/test_terminal.py::test_cancelled_tool_does_not_start -q -p no:cacheprovider --basetemp $testTemp
```

预期是这些测试全部 `passed`。它们分别验证：一次超时后第二次成功；连续故障达到两次上限；取消标记使下一个工具不启动；第一次供电提取工具失败后，`/retry` 对应的服务从完整检查点恢复并生成报告；原失败 run 与新成功 run 都保留。测试使用合成资料和固定模型响应，不访问真实模型，不修改上面的真实任务。

在真实终端，如果 `/status` 显示**执行失败**且没有等待或未完成节点，可输入 `/retry`。预期出现“已从失败运行重新尝试”和新的程序报告。`/retry` 每个任务最多使用一次；失败发生在图节点中途时会拒绝，避免重复执行可能已有副作用的步骤。`/cancel` 用于请求停止运行，程序在下一个工具边界检查；取消已保存的人工等待点会终止该等待，后续需另建任务。它不保证立刻停止正在进行的模型调用。若想在同步终端执行期间取消，需要在第二个终端打开同一任务输入 `/cancel`。

## 技术边界与记录

供电提取使用独立 Python 子进程，单次限时 **15 秒**，临时故障最多尝试 **2 次**，超时子进程会被终止。格式不匹配是资料问题，不重复尝试。子进程只计算证据，不写业务记录，因此工具级重试不会生成两条有效审核。Agent 图仍限制 40 个执行步骤，模型客户端已有单请求超时和有限重试。失败运行不会被当成器件“不满足”；`/status` 展示执行状态，`/report` 展示供电结论。运行清单记录供电提取尝试次数及恢复来源。

取消是协作式的，在工具边界和图返回后生效，不直接强杀任意模型请求。恢复只覆盖检查点已有完整状态、没有待执行节点的失败运行；强杀、数据库损坏、任意节点回放、跨业务库和检查点的原子提交均不在本轮保证内。两个任务各有独立存储和写锁。
