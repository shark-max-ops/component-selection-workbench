# A3.2：显式等待与同线程恢复

在已经完成供电核验的任务上，用命令建立一个审核或澄清等待点。程序通过 LangGraph `interrupt()` 暂停，保存真实中断 ID；`/resume` 使用 `Command(resume={中断ID: 回答})`，继续同一个 `thread_id`、同一个 `checkpoints.sqlite` 中的 Agent 图。

本轮选择显式等待边界，尚未让模型自行决定在任意工具中断，也未自动在首次核验末尾暂停。已有完成任务和 A3.1 的直接审核入口继续可用。

## 审核实践

在 backend 执行：

```powershell
uv run python -m scripts.run_terminal
```

打开一个最新运行成功的任务，在工作台输入：

```text
/open 任务ID
/wait-review
/status
/exit
```

重新运行启动命令，打开相同任务：

```text
/open 同一个任务ID
/status
/evidence
```

状态中的 `execution_status` 为 `waiting_input`，`pending` 列出中断 ID、问题及等待开始时的审核版本。对照绑定 PDF 核对参数及适用条件，再提交审核。以下假设当前审核版本是 0：

```text
/review practice-001 | 0 | 姓名 | approve | 已对照PDF核对参数及适用条件
/resume 从status复制的中断ID | practice-001
/report
```

`/review` 保存审核并运行程序规则，不会自动恢复图。`/resume` 必须引用等待开始后新增的最新审核请求，恢复后继续调用模型整理解释并校验报告。`reject` 也可以用于恢复，供电结果保持 unknown。审核人仍是本地操作者声明，没有身份认证。

## 澄清实践

```text
/ask 是否需要进一步解释供电判定中的待确认项？
/status
/resume 从status复制的新中断ID | 请解释待确认项
```

澄清答案保存于 `human_response` 并成为后续模型输入；原需求不会由答案自动改写。新的需求需新建任务。

等待期间，普通消息会提示使用 `/resume`。错误或跨任务的中断 ID、空答案、已经完成恢复的旧 ID 都会被拒绝。重复建立等待也会被拒绝。等待和审核本身不调用模型，但恢复后的 Agent 会调用真实模型，除非运行离线测试。

## 代码与边界

- `agents/human_input.py`：定义等待状态和 `AwaitHumanInput.before_agent()`；中断前无业务写入，节点重放不会重复提交审核。
- `services/task_service.py`：`wait_for_input()`、`resume_task()` 共用原任务写锁；查询从检查点 pending writes 读取真实中断，显式区分普通消息与 Command。每次等待和恢复有独立 run，恢复清单记录中断 ID 和审核版本。
- `cli/terminal.py`：增加 `/wait-review`、`/ask` 和 `/resume`。无需重新创建任务或生成新的 thread。

审核库与图检查点没有跨库事务。如果审核已提交但尚未 resume，任务仍保持等待，重新打开后可以继续。若 resume 已消费中断但后续模型失败，当前不自动重试或回放该恢复操作；这属于 A3.3 的失败处理范围。Ctrl+C 或强杀发生在任意模型/工具执行位置也不保证恢复，只有已保存的显式等待点在本轮覆盖内。

## 验证

离线测试使用固定模型响应、合成资料和实际 LangGraph/SQLite。主进程完成核验并暂停，独立的 uv 子进程重建业务对象与 Agent 后恢复同一 thread，验证审核结果一致；另验证澄清、普通消息拒绝、错误/跨任务 ID、旧 ID 重复恢复，以及终端命令分发。本轮没有调用真实模型或替用户审核真实 PDF。

在 backend 运行：

```powershell
uv --cache-dir ../runtime/uv-cache run --offline --no-sync ruff check app scripts tests
$testTemp = Join-Path (Resolve-Path ../runtime) ("tests-a32-" + [guid]::NewGuid().ToString("N"))
```

项目内缓存用于避开当前执行环境的默认缓存访问限制，`--no-sync` 使用已安装且已锁定的项目环境。
